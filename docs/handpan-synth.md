# Hybrid handpan synthesizer

`AudioSynthHandpan` combines an optional caller-supplied mono PCM16 attack with
a bank of damped resonators. The examples synthesize their own short attack,
so no recorded handpan sample is required. The class supports three body modes
and three optional upper partials; the low-CPU phrase preset leaves the upper
partials disabled so they cannot sound like a second melodic instrument. A restrained soft-saturation blend can add mild harmonic roughness, but the
examples prioritize avoiding peak overload by reducing resonator and attack gain. Resonators are independent per configured pad, and repeated
strikes add energy to existing states instead of cutting off the previous ring.

## Limits and runtime behavior

- Up to 16 configured pad slots, six modes per pad and eight concurrent attack
  sample voices.
- A fixed 16-entry event ring buffer accepts note events without dynamic
  allocation. Its usable capacity is 15 queued events; `noteOn()` returns false
  for an unconfigured pad or a full queue.
- Velocity is 0..127 and scales both the attack sample and each resonator mode.
- The class produces mono PCM16. Connect its output to both I2S channels or to
  a mixer as needed.
- Decay is specified as `T60`, the time for modal amplitude to fall by 60 dB.
- The sample pointer is retained, not copied. Keep its data alive and unchanged
  during playback; `const` samples mapped from flash are suitable.
- Configure the pad bank before starting audio updates (normally in `setup()`
  before `AudioMemory()`). Configure again after changing the global sample rate.
- If `noteOn()` returns false, the event was not queued and should be retried or
  counted by the application. Calls are block-scheduled by the current audio
  graph, so the onset resolution is one audio block, not per-sample MIDI timing.

## How the synthesis works

Each configured pad is a small hybrid instrument. A note combines two signals:

1. **Attack transient (PCM sample).** A short mono signed 16-bit PCM waveform
   provides the noisy, high-frequency part at the start of the strike. The
   example generates a deterministic 30 ms transient at startup from decaying
   broadband noise plus two rapidly decaying sine rings. It is not a recording.
   One attack buffer is currently shared by all 16 pads.
2. **Damped resonator bank.** Six independent second-order resonators provide
   the sustained tone: three body modes and three upper partials that establish
   the metallic ring. Every pad has its own frequency, gain, decay and phase
   values, so each note has a different modal balance and ringing character.

The output of a resonator is generated by the recurrence

`y[n] = 2 r cos(ω) y[n-1] - r² y[n-2]`

where `ω = 2π f / fs`, `f` is the configured mode frequency, `fs` is the
audio sample rate, and `r` is the per-sample decay factor. For a requested
amplitude decay time `T60`,

`r = 10^(-3 / (T60 × fs))`

because a 60 dB amplitude reduction is a factor of 0.001. The coefficients are
calculated in `configureNote()`, not inside the audio-block hot loop.

On `noteOn(pad, velocity)`, the velocity is normalized to 0..1 and scales both
the PCM attack and the modal gains. A phase-shaped impulse is added to the
resonator's existing state. **The states are not cleared on retrigger**, so a
new hit adds energy to an already-ringing note rather than cutting off its tail.
The modal outputs and active attack voices are accumulated in a floating-point
mix buffer. Optional soft saturation then shapes the combined waveform before
it is clamped and converted to PCM16. The H2 curve is `tanh(1.8 * x) / 1.8`;
`update()` uses a bounded rational approximation to avoid a per-sample `tanhf()`
call. Set saturation to zero to bypass the non-linear stage; the examples use
amount `0.25` for a restrained H2 blend; modal, attack and mixer gains are also lower to leave more headroom. Strongly overlapping notes can still overload
the final range, so choose modal gains and graph gain accordingly.

The PCM sample pointer is retained by the synthesizer, not copied. It may point
to a caller-owned RAM array or a `const int16_t[]` table placed in flash, but
the data must remain available and unchanged for the lifetime of playback. The
example's generated attack buffer is writable RAM because it is built at
startup. A licensed recording can be converted to a short mono PCM16 table and
used instead; no WAV parser or filesystem is built into `AudioSynthHandpan`.
The configured sample rate is used to calculate a 32-bit fixed-point playback
increment, so a 44.1 kHz attack can be interpolated at a 48 kHz output rate.

The class supports 16 pads × 6 modes (96 configured resonators) and up to eight
concurrent PCM attack voices. The 96 modes are not all necessarily active at
every instant: quiet modes are culled once per block. If all eight attack voices
are busy, the voice with the least playback time remaining is replaced by a new
attack. This keeps the onset responsive, but an extreme burst can truncate a
previous transient.

## API

```cpp
AudioSynthHandpan handpan;

AudioSynthHandpan::ModeConfig modes[6] = {
    // frequency Hz, peak gain, T60 seconds, phase radians
    {146.8f, 0.3850f, 3.00f, 0.12f},
    {295.2148f, 0.0560f, 3.00f, 1.10f},
    {438.0512f, 0.2880f, 4.00f, 2.05f},
    {786.8480f, 0.0000f, 0.25f, 0.72f},
    {874.9280f, 0.0000f, 0.12f, 2.20f},
    {1583.9720f, 0.0000f, 0.08f, 1.48f},
};

// Optional soft saturation (0 = bypass, 1 = full H2 curve).
handpan.setSaturation(0.25f);
// attack is a caller-owned signed mono PCM16 sample; nullptr disables it.
handpan.configureNote(0, modes, 6, attack, attackSampleCount, 44100, 0.03f);
handpan.noteOn(0, 100);
```

`ModeConfig::gain` is a normalized peak amplitude per mode (0..1), not a
percentage. `attackGain` is an additional normalized linear gain applied to the
sample. The selected phrase preset follows variant C from the offline comparison. It
keeps the S3-like body-mode ratios `1.000, 2.011, 2.984` with `T60` values
`3.00, 3.00, 4.00 s`; their per-pad gains are shaped by a level table. The upper
partial ratios `5.36, 5.96, 10.79` remain configured but have zero gain in these
examples. `AudioSynthHandpan::triggerNote()` skips zero-gain modes, so only the
three body resonators need to run during the sustained tail. This is the lowest-
compute model among the previously compared variants, and avoids a separate
pitched metallic line. The procedural attack gain is `0.03`, the generated attack is normalized to a 0.65 full-scale peak, and the musical/load-test examples use lower modal levels and a restrained `0.25` saturation blend. `setSaturation(0.0f)` bypasses the non-linear
stage; intermediate values blend dry and saturated outputs. These are
experimental listening parameters, not measured physical modes of a particular
handpan; confirm them by listening on target hardware.

## Example and recordings

There are two separate sketches:

- `examples/Synthesis/HandpanMusic/HandpanMusic.cpp` is the musical example:
  an approximately 96-second handpan arrangement of Beethoven's public-domain **“Für Elise”** theme. It revisits the opening motif, includes answering phrases and a contrasting middle section, then returns to the theme and coda. It uses a regular sixteenth-note grid, variable velocities and a restrained Freeverb return.
- `examples/Synthesis/Handpan/Handpan.cpp` is the diagnostic/load-test sketch.
  It runs a moderate melody, a realistic phrase and increasingly dense pad
  patterns, reporting CPU load, audio-block use and rejected note events.

Both examples generate the short procedural attack at startup and do not depend
on any third-party recording. Applications may pass a caller-owned mono PCM16
attack or a `const int16_t[]` flash table when they have appropriate rights to
that audio; passing `nullptr` disables the sampled transient. Do not redistribute
extracted reference samples unless their license explicitly permits it. The notes
and tuning here are illustrative starting parameters, not measurements of a
particular commercial handpan.

## Performance notes

`update()` performs no trigonometric or exponential calculations; modal
coefficients are prepared in `configureNote()`. Attack-sample interpolation uses
32-bit fixed-point arithmetic on purpose; the phase fraction loses its lowest
Q16 bit to avoid a 64-bit multiply in the real-time loop. Active resonators and active
attack voices are processed, and silent resonators are disabled once their
state falls below the output threshold. If the audio block pool is temporarily
exhausted, oscillator states and attack positions still advance to preserve
wall-clock decay. Actual CPU cost must be measured on the target, particularly
with all 16 pads ringing and eight attack voices active; the included example
prints `AudioProcessorUsage()` and audio memory usage on the device.


## Reverb and worst-case load test

The musical and load-test sketches route the source to a dry path and to
mono `AudioEffectFreeverb`, then blend them through `AudioMixer4`. The musical
example starts at 0.84 dry / 0.18 wet; the load test uses 0.82 dry / 0.22 wet.
Both use room size 0.68 and damping 0.46. These are listening defaults, not
calibrated acoustic-room parameters. Freeverb allocates its delay lines once in
`setup()`; both examples request 32 audio blocks to cover the source, reverb
return and final mixer. Both default to 48 kHz and configure I2S before
`AudioMemory()` and before calculating the resonator coefficients. Change the
respective `HANDPAN_MUSIC_SAMPLE_RATE` or `HANDPAN_TEST_SAMPLE_RATE` macro to
`44100` for a 44.1-kHz run.

The Für Elise arrangement uses equal-tempered pitch values from G#3 to F5. Its 96-second loop is organized as twelve 8-second sections: opening motifs, lower answers, a contrasting middle section, theme returns and a coda. The notes are arranged for the available handpan pitch bank; this is a stylized arrangement rather than a note-for-note transcription of the full piano score.

The example defaults to **48 kHz**. It calls `audioOut.setSampleRate()` before
`AudioMemory()` and before configuring the resonators, so the modal coefficients
match the selected rate. For a direct 44.1-kHz comparison, change
`HANDPAN_TEST_SAMPLE_RATE` from `48000` to `44100` near the top of
`examples/Synthesis/Handpan/Handpan.cpp`, rebuild, and compare the same phases.
The generated attack remains a 44.1-kHz source sample and is resampled by the
synthesizer during playback. The ES8311 is initialized with its sample-rate-specific
clock configuration; the ES8388 follows the I2S output clock.

The example cycles through five eight-second phases:

1. `MELODY + HALL`: a moderate overlapping melody, useful as a baseline.
2. `REALISTIC HANDPAN PATTERN`: a looser 96-BPM-inspired phrase with varied
   velocities, rests, occasional quiet grace notes and longer ringing overlaps.
   The phrase is illustrative, not a transcription of a real performance.
3. `ALL 16 PADS / BODY TAILS`: each pad is struck in turn, about once per
   second, so the long body resonances overlap. This checks every pad slot and
   tail overlap, but by itself does not guarantee that all six modes per pad
   remain active simultaneously.
4. `RAPID 4-NOTE BURSTS`: four pad events every 24 ms, stressing the event queue
   and the eight attack-sample voice limit while modal tails remain active.
5. `DENSE 16-PAD SWEEP / BODY LOAD`: four pad events every 12 ms, covering all
   16 pads within 36 ms and revisiting each pad about every 48 ms. With the
   upper partials disabled by the low-CPU preset, this phase is intended to keep
   up to 48 body-mode resonators active together after startup. It is a synthetic
   worst-case load test, not a realistic playing pattern, and may sound rough or
   clipped. Keep the output volume low during this phase.

Once per second the serial log reports graph-wide CPU, per-stream CPU for the
handpan source and Freeverb, current/peak audio-block use, and note events
rejected by the synthesizer. Let each phase run for several seconds when
comparing boards. The measured maximum is specific to the test run; it is not
a guarantee for every sample rate, compiler optimization, Wi-Fi load or effect
chain. Listen for clipping or roughness during the intentionally extreme stress
phase as well as checking CPU headroom.

The example generates its own short procedural attack. A caller-owned PCM16
attack can be substituted without changing the synth architecture, provided the
application has permission to use that audio.


## Resonator-loop optimization

The resonator bank processes each active mode over a complete audio block. Its coefficients and two delay states are kept in local variables inside that block loop; state is written back once per mode, and silence detection is performed once per block. This reduces repeated state loads and per-sample mode-management work when many pads are ringing. The `mixBuffer` adds `AUDIO_BLOCK_SAMPLES * sizeof(float)` bytes to each synthesizer instance (512 bytes with 128-sample blocks). Verify CPU load again on the target after rebuilding.
